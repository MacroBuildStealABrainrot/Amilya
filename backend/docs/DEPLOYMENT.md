## Why the private path is feasible

Cloud Run Direct VPC egress supports network tags and private-range routing without a connector. Its subnet must be `/26` or larger. Only the application tag receives access to PostgreSQL port 5432; administrative SSH is limited to Google's IAP range and authorized OS Login identities. A private VM can reach supported Google APIs and Artifact Registry using Private Google Access. The VPC's default internet-gateway route remains necessary for that Google API path even though the VM has no external IP. [Direct VPC configuration](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc), [Private Google Access](https://docs.cloud.google.com/vpc/docs/private-google-access), [configuration requirements](https://docs.cloud.google.com/vpc/docs/configure-private-google-access)

Container-Optimized OS supplies the container runtime and registry authentication support. This avoids a first-boot dependency on external Debian package repositories, which Private Google Access does not generally make reachable. Mirror a reviewed official PostgreSQL 17 Alpine image into the project repository before starting the VM. The VM fetches that private image and its bootstrap password using its own narrowly scoped service account. COS and PostgreSQL still need a patch/upgrade process; an unattended update assumption is insufficient. [COS container execution](https://docs.cloud.google.com/container-optimized-os/docs/how-to/run-container-instance), [COS automatic update limitations](https://docs.cloud.google.com/container-optimized-os/docs/concepts/auto-update)

## Database initialization, TLS, and migrations

The startup script is intentionally fail-closed on an unformatted disk, missing TLS, missing configuration, or an unpinned image. It does not format, delete, or silently replace database storage. These are the repeatable bootstrap procedures; the pilot's completed execution and verification are recorded in `CLOUD_EXECUTION.md`:

1. Verify the newly created retained disk is exactly `/dev/disk/by-id/google-wcp-data`, distinct from the boot disk. Initialize only that explicitly verified empty data disk as ext4, then mount it at `/mnt/stateful_partition/wcp/data`. Never format a disk discovered by a broad search or containing existing data.
2. Copy `deployment/postgresql.conf`, `pg_hba.conf`, and `pg_ident.conf` to `/mnt/stateful_partition/wcp/`. Store the reviewed `REGION-docker.pkg.dev/PROJECT/wcp/postgres@sha256:DIGEST` reference in `postgres-image.txt`. The supplied script expects the Alpine PostgreSQL user ID 70 and verifies it at runtime.
3. Provision a private CA and a server certificate with `IP:10.30.0.10` in its subject alternative names. Keep the CA private key outside the VM/application. Place the server certificate and key in `tls/server.crt` and `tls/server.key`; the script sets PostgreSQL ownership and restrictive key permissions. Upload only the public CA certificate to the runtime CA secret. Define certificate renewal and alert ownership.
4. Create a random bootstrap password as `wcp-db-owner` using a protected file and Secret Manager input-from-file. Never put the password in VM metadata, shell history, command arguments, build arguments, or logs. The script retrieves it to a root-only `/run` file and initializes the local `wcp_owner` role. Changing the secret later does not automatically change an existing PostgreSQL password: perform a coordinated database password rotation.
5. Start the script through the VM's reviewed startup mechanism. Check TLS, PostgreSQL readiness and disk retention. Host administration uses IAP and `docker exec --user postgres` with the local peer mapping to `wcp_owner`. The verified source of IAP SSH host forwarding is this VM's private IP `10.30.0.10/32`; only that exact address receives TLS/password owner access. Other addresses in the VPC runtime subnet can authenticate only as the application role.
6. Run the application's Alembic migrations as the owner through the controlled IAP tunnel. Use a loopback-only local listener, `host=10.30.0.10`, `hostaddr=127.0.0.1`, the forwarded port and `sslmode=verify-full` with the generated CA. This preserves certificate identity while connecting through the tunnel. Remove the tunnel after operator work. Do not run schema creation automatically when serving requests.
7. Create a distinct login `wcp_app` with a separately generated password and no superuser, role-creation, database-creation, replication or bypass-RLS rights. Grant connection/schema use and required table/sequence privileges, including migration default privileges. Run `deployment/harden_runtime.py --apply` with protected owner/runtime URL files after initial migrations. It revokes UPDATE/DELETE on the six append-only clinical tables, `audit_events` and `credit_ledger`, then verifies all 16 denied writes using rollback. Runtime SELECT/INSERT remain; mutable encounter, fact, workspace, provider and billing state retain their required updates. Reapply and review the table list when future migrations introduce immutable tables. The owner retains schema migration and disaster recovery authority.
8. Put the `wcp_app` URL in the runtime environment secret using the installed PostgreSQL driver, `sslmode=verify-full`, and `sslrootcert=/run/db-ca/ca.crt`. Cloud Run requires the separate CA secret to use a different mount directory from `/run/secrets/app.env`. Test a successful connection, wrong-CA failure, plaintext rejection, unauthorized owner-login rejection and tenant isolation before admitting traffic.

The database is configured with 30 connections, 64 MB shared buffers, bounded WAL, a 700 MB container limit and small work buffers. These limits passed the synthetic workflow and reboot checks; they are not load-test evidence. The server currently has a five-connection pool plus five overflow connections per process. Run one application worker and keep migration connections separate. Even with a service maximum of one, deployment overlap and platform behavior can temporarily require additional capacity; prove memory and connection headroom. A single small VM and single retained disk have no standby or point-in-time recovery.

## Runtime and release sequence

Store application configuration in a mounted Secret Manager environment file selected by `WOUNDCOPILOT_ENV_FILE`. Pin secret versions in the Cloud Run revision. Set `ENVIRONMENT=production`, a strong stable `APP_SECRET`, an explicit HTTPS `PUBLIC_BASE_URL`, exact `TRUSTED_HOSTS`, `SECURE_COOKIES=true`, `AUTO_CREATE_SCHEMA=false`, `TEST_PROVIDER_MODE=false`, and the verified PostgreSQL URL. Start with `CLINICAL_DATA_ENABLED=false`, provider execution disabled, billing disabled, and no credential values in frontend assets. Do not persist a bootstrap admin password in the runtime environment; use the repository's administrator bootstrap CLI through a controlled operator session.

Deploy the service privately for validation. Configure the final URL, origin/cookie settings, secrets, signed document export, database restore, provider privacy approvals and billing fixture/live-test gates before granting public invocation. The eventual public service still enforces application login, CSRF, workspace membership and platform-admin permissions. Add Stripe's signature-verifying webhook destination only after the deployment URL and price IDs have been verified. No card information or provider keys belong in the browser.

Before any patient data, complete a backup plus restore drill into an isolated database; define retention, recovery objectives, monitoring and an operator on call; establish regional/cross-border disclosure and provider approvals; resolve the Privacy/Terms owner placeholders and legal review; and pass the clinical release criteria. A US Free Tier database is a cross-border hosting choice for Canadian users and needs an explicit organizational decision. The free infrastructure proposal cannot establish PHIPA/PIPEDA compliance or replace a healthcare custodian's agreements and risk assessment.

Keep one verified application revision for rollback within measured registry capacity. Do not remove images required for rollback or restart solely to meet a storage allowance. Before PostgreSQL major upgrades, test dump/restore and extension compatibility; do not swap major-version images against the existing data directory. Stopping the VM does not stop persistent-disk charges outside any remaining allowance. No destructive cleanup or automated billing-disable action is included, because either can interrupt access to clinical records.

The plan generator and configuration have been reviewed locally; plan-policy tests cover unsupported regions, over-30-GB disks, mutable image references and paid-resource exclusions. The PowerShell file was parsed locally and then used for an authorized read-only account inventory. Execution status for VM bootstrap, TLS, restore and Cloud Run connectivity is recorded separately in `CLOUD_EXECUTION.md`; do not infer completed checks from the command proposal. The final retained image footprint must be measured against the account's registry allowance.

Database initialization, TLS, migrations through `0003`, runtime append-only grants, signed-workflow reboot durability and an encrypted off-VM restore have passed. The root operator records final application revisions and release checks separately. Remaining clinical gates include owner recovery-key custody, sustainable retention and backup-cap response, monitoring/on-call ownership, load and recovery objectives, legal/cross-border review, provider privacy approvals and billing activation checks. A resilient clinical service requires a separately agreed availability and spending model.

Billing remains disabled for the deployed pilot. The adapter's synthetic fixtures cover current-cycle payments, duplicate events, upgrades, renewals, failure, cancellation, top-ups and refunds. A paid invoice whose cycle has not started returns a retryable error while preserving the current cycle; it is applied when retried at the boundary. Long-future invoices beyond Stripe's automatic retry window need operator replay. Scheduled deferred entitlements are not implemented, and fixture success is not a claim of production Stripe readiness.
